Offer Engine Architecture

Personalised Offer Engine

How a simulated Customer's behaviour becomes an Offer on Telegram, and why the engine never sees the answer key.

Simulated world (reads Ground Truth) Offer engine (never reads Ground Truth) Outside service or people Ground Truth boundary

Five decisions hold it together

ADR 0001Rules before the agent
Rules work out the Eligible Set. The agent picks one Offer or No Offer from it. Validation re-checks every Rule, and a rule-based Fallback runs on failure.
ADR 0002Hidden Ground Truth
Each Customer's real buying chance per Offer Type lives in the sim_* tables. Only the simulated world reads it. The engine learns Estimated Lift from past random Offers instead.
ADR 0003Simulation Clock
Rules, events and expiries all run on simulated time, advanced from the console. Only Telegram delivery uses the wall clock.
ADR 0004Bounded Customer Bots
Ground Truth sets the base chance of buying. Claude nudges it by at most ±30% for how well the message fits, and a weighted coin flip decides.
ADR 0005Offer Card terms from code
Code draws the amount, minimum basket, category and expiry from the validated Offer. The agent writes only the caption.

The goal

A discount sent to someone who would have bought anyway is lost margin. So the engine aims at Incremental Margin, picks the cheapest Offer that captures the Lift, and is happy to send No Offer.

Who decides

The Claude agent decides for chat-attached Customers: the Customer Bots and the Testers' copies. The rules chooser decides for everyone else in the ~10k world, and steps in as the Fallback when the agent fails or its answer breaks a Rule.

Where it runs

offer-engine start (or make) runs the four processes together: Offer Bot, Customer Bot simulator, console and live view. For judging, one Docker container runs them and a Cloudflare Tunnel serves the console and live view (T29, in progress).
