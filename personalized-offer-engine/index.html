Personalised Offer Engine. A Claude agent picks one offer or no offer for each customer, inside rules set by the marketing team. All data is synthetic.

The idea

A discount sent to someone who would buy anyway is lost margin

Persuadable

Buys only with an offer.

Send the cheapest offer that works

Sure Thing

Buys anyway.

No Offer

Lost Cause

Won’t buy either way.

A free ₹0 reminder at most

Sleeping Dog

An offer makes them less likely to buy.

No Offer

So the engine aims at Incremental Margin: the margin an offer adds minus what it costs. It does not aim at likelihood to buy.

Each customer’s true type is hidden from the engine. It only sees an estimated lift, learned from past offers that were sent at random.

The four groups are the Response Classes. They come from each synthetic customer's hidden buying-chance formula (Ground Truth). Only the simulator reads Ground Truth; the decision pipeline never does.

How it is built

Rules set the limits, Claude chooses inside them, code checks every choice

Trigger

Abandoned cart, points expiring, long gap, first delivery, the Daily Sweep or /offers

Rules

Opt-out, Holdout, caps, budget and margin floor give the Eligible Set of offers

Valuation

Estimated lift × margin − expected cost, per option

Agent

Claude picks one option or No Offer, sets its terms and writes the caption

Validation

Re-checks every Rule and the caption. On failure the rule-based Fallback decides

Offer

Code draws the Offer Card from the validated terms; the Offer Bot sends it on Telegram

Stack

Python 3.12, SQLite

Claude Opus 5.5 decides; Haiku 5.5 plays the customers

Telegram bots (polling)

FastAPI live view, Streamlit console

Synthetic world: 10,000 customers, 12 months of history

Docker on AWS Lightsail, Cloudflare Tunnel

985 tests

The agent decides only for chat-attached customers (the Customer Bots and people testing on Telegram). The rule-based chooser decides for the other ~10,000, and is also the Fallback. Five ADRs in docs/adr record the settled design choices.

Saving margin

A discount goes only where it adds margin

Each option is worth estimated lift × margin − chance of redemption × cost. Here 7% off fashion is worth ₹10; 5% off electronics would lose ₹26.6.

Where

Live engine view › Saving margin

Try it

  1. Click “A Customer a discount moves gets one”.
  2. Click the Valuation stage.
  3. Compare with “A Lost Cause gets a ₹0 Nudge”.
Estimated lift is learned from past offers in the synthetic history that were sent at random, like A/B tests. Version 1 averages them per customer segment.

Hard limits

Some customers never reach Claude

Opt-out is absolute. The 10% Holdout never gets offers, so lift can be measured. Three “Not now”s in 14 days pause offers for 14 days.

Where

Live engine view › Hard limits

Try it

  1. Click “Three Not nows pause Offers”.
  2. Open Checks: the Fatigue Pause stopped it.
  3. Try the Holdout and Opt-out scenarios too.
The Checks run before the Eligible Set is built, so the agent is never asked about these customers. Each Decision records its Binding Rule.

Safety net

The Caption Check blocks invented urgency

Claude writes only the caption; code draws the terms on the card. A caption with a wrong number, a made-up deadline or pressure words never goes out.

Where

Marketer controls

A Rule change flips the next Decision

Rules read as sentences. Each save is a new version; offers already sent keep theirs. Here bronze goes from 15% to 5% max, and the same customer’s offer drops from 7% to 5%.

Where

  2. Press Preview impact, then Save.

Simulated customers

Customer Bots reply in character

Seven Telegram bots each play one customer from a persona card. Ground Truth sets the buying chance; Claude may move it by up to ±30% for message fit; a coin flip decides.

Where

Live view › any scenario › What the Customer did

Try it

  1. Click “A Lost Cause gets a ₹0 Nudge”.
  2. Scroll below the stages: the card, the chance, the flip and the bot’s reply.
The ±30% cap keeps the role-play from overruling Ground Truth, so outcomes stay measurable (ADR 0004). Customer Bots use Claude Haiku 5.5.

Simulated world

10,000 customers run on a Simulation Clock

Each simulated hour, every customer visits, carts, orders and earns points; Triggers fire and sent offers resolve. The Daily Sweep decides for everyone at 10:00. A day takes about 15 s.

Where

Console › Simulation Clock · Live view › The world so far

Try it

  1. Console: press +1 day.
  2. Live view: counters and charts update as it runs.
Every Rule, event and expiry uses simulated time, never the wall clock (ADR 0003). Wall-clock time is used only for Telegram delivery. The world starts at 1 Dec 2026, after 12 months of generated history.

Results

A blanket discount loses money; targeting earns ₹23–29 per ₹ spent

Policy, 28 simulated daysIncremental Margin per ₹
No Offers (baseline)0
Blanket 20% off−0.08
Rules Only+28.93
Rules + Claude agent+22.60

Measured by offer-engine simulate on a 500-customer sample of the 10k world, each Policy on its own copy from the same start and seed.

The agent scored below the rules chooser: +₹13,052 against +₹20,887. Part of the gap may be noise; it is one seed and one month.

Incremental Margin = margin from orders the offer caused − offer cost, against No Offers. Full run: about 100 minutes.

Rules Only's per-rupee figure is high partly because many of its offers are ₹0 Nudges, which add margin at no spend. Blanket 20% ignores most Rules by design. The console's Results page shows the live funnel against the Holdout and spend wasted on Sure Things.

What to know before you test

Known limits

  • One shared world with no password: anyone can change Rules or press Reset.
  • Claude decides only for the 7 Customer Bots and Telegram testers; the rules chooser decides for the rest.
  • A Customer Bot reply takes about 10 s.
  • Results are from one seed and one simulated month.
